# `viewset` — Overview & Introduction

`viewset` is a generic, Django-REST-Framework-inspired CRUD toolkit for building
admin-style REST APIs on top of **actix-web**, **sqlx**, and **Postgres**. It's
part of the `actixutils` crate.

Its goal: given a struct that describes a database table, generate a fully
working REST resource — `GET /things`, `POST /things`, `GET /things/{id}`,
`PUT`/`PATCH /things/{id}`, `DELETE /things/{id}` — with pagination, sorting,
filtering, and search, without hand-writing SQL or handler boilerplate for
every entity in your admin panel.

## Design philosophy

Every entity in an application tends to need the same handful of endpoints
and the same handful of concerns: list with pagination, look up by id,
validate and insert, validate and patch, and delete (or soft-delete). Writing
that by hand for every table is repetitive and error-prone. `viewset` factors
that repetition into four layered traits, each with a default implementation
built from static metadata about your entity — so a new resource typically
needs only:

1. A struct describing the entity's columns and DTOs.
2. A `const` metadata block (table name, columns, field types).
3. A few trait `impl` lines to plug it into the stack.

Anything the defaults don't cover — a join, a computed value, a permission
check, a transactional write — is a normal Rust method you override. Nothing
is hidden behind reflection or runtime configuration; every piece of
metadata is a compile-time `const` or associated type.

## The four-layer architecture

Requests flow down through four traits; responses flow back up:

```
HTTP request → ViewSet → Service → Repository → Database
```

| Layer | Trait | Responsibility | Talks to |
|---|---|---|---|
| HTTP | `ViewSet` | Extracts requests, calls the service, translates results into `HttpResponse` | actix-web |
| Business logic | `Service` | Validation, authorization, hooks, transactions | `Repository` |
| Data access | `Repository` | SQL only — no validation or business rules | `sqlx::PgPool` |
| Metadata | `Entity` | Static description of the table, columns, and DTOs | — |

Each layer is a trait with mostly-working default methods, so you only
override what needs to differ from the generated behavior. A default
`DefaultRepo<E>`, `DefaultService<R>`, and `DefaultViewSet<S>` exist so a
fully default stack requires zero custom `impl` blocks beyond `Entity`.

### `Entity` — static metadata

`Entity` is the contract every other layer is generated from. It has no
methods to speak of beyond extracting the primary key — everything else is
associated types and `const`s:

- `Id`, `CreateDto`, `UpdateDto`, `ResponseDto` — the four shapes a resource
  needs: primary key type, `POST` payload, `PUT`/`PATCH` payload, and the
  shape actually sent back to clients (kept separate from the entity so
  internal columns never leak into a response).
- `TABLE`, `PK_COLUMN` (defaults to `"id"`), `COLUMNS` — where and what to
  query.
- `FIELDS` — a `(column name, SqlType)` list used to bind `INSERT`/`UPDATE`
  values with their real Postgres type instead of coercing everything
  through `jsonb`.
- `SEARCHABLE`, `SORTABLE`, `FILTERABLE` — allow-lists that gate which
  columns a client can search, sort, or filter on via query parameters.
- `SOFT_DELETE_COLUMN` — an optional column that turns `DELETE` into an
  `UPDATE ... SET column = now()` and filters deleted rows out of `list`/
  `retrieve`.

In practice this impl is generated by `#[derive(Entity)]` (from the
companion `viewset-macros` crate) from attributes on your struct's fields,
rather than written by hand.

### `Repository` — data access

Default methods (`list`, `retrieve`, `create`, `update`, `delete`, `exists`,
`count`) build SQL dynamically with `sqlx::QueryBuilder`, entirely from
`Entity` metadata — no per-entity SQL to write. Two of the defaults,
`insert_columns` and `update_columns`, are the bridge between your DTOs and
the database: they serialize the DTO to a JSON object and, for every field
named in `Entity::FIELDS`, pull out a correctly-typed `SqlValue` so Postgres
sees a real `i32`/`Uuid`/`Decimal`/timestamp parameter — never a `jsonb`
blob standing in for a typed column.

Because `UpdateDto` fields are conventionally `Option<T>` with
`#[serde(skip_serializing_if = "Option::is_none")]`, a field that's simply
*absent* from the JSON is a field the update leaves untouched — that's what
gives `PATCH` real partial-update semantics without a separate "was this
field provided" wrapper type.

### `Service` — business logic

`Service` delegates its default `list`/`retrieve`/`create`/`update`/`delete`
straight to the `Repository`, wrapped in a symmetrical set of `before_*` /
`after_*` hooks (all no-ops by default). This is the layer where you add
permission checks, extra validation, transactions, cache invalidation, or
event publishing without touching the CRUD wiring or the SQL itself.

### `ViewSet` — HTTP

`ViewSet::configure` wires a `web::ServiceConfig` up with the standard REST
routes for a resource — list/create on the collection path, retrieve/update/
delete on `{path}/{id}` — and each handler (`handle_list`, `handle_create`,
etc.) is itself an overridable trait method, in case you need to change how
a request is parsed or a response is shaped for one particular resource.

## What's out of scope

`viewset` deliberately doesn't decide:

- **Authentication.** `RequestContext<U>` carries a generic, optional
  `user: Option<Arc<U>>` — your application implements `FromRequest` for it
  against whatever auth middleware it uses.
- **Multi-tenancy enforcement.** `RequestContext` carries an optional
  `tenant_id`, but scoping queries by tenant is left to your `Repository`/
  `Service` overrides.
- **Complex queries.** Joins, aggregates, and window functions aren't
  generated — override the relevant `Repository` method and write the SQL
  by hand for that one case.

## When to reach for `viewset`

It's a strong fit for internal admin panels, back-office CRUD APIs, and
any resource that's "a Postgres table with a REST wrapper around it" —
exactly the territory Django's admin/DRF viewsets cover on the Python side.
It's a poor fit for resources whose primary operations aren't row-level CRUD
(complex workflows, aggregation endpoints, streaming) — those are better
written as plain actix-web handlers that reuse `RequestContext` and
`ApiError` for consistency, without going through `ViewSet`.
